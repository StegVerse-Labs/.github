# StegVerse SDK, Manifest Builder and Publisher — evaluator-independent capability and version roadmap

**Scope:** Entire StegVerse ecosystem, every eligible external framework and evaluator. **This is not an ÉLAN roadmap and no individual experiment controls general release scope or timing.** Revised 2026-09-25 from exact repository source; target versions after the existing RC are proposals until independently admitted and authorized through the canonical Task Registry and native component owners.

## Governing delivery contract

Any evaluator can declare source-native data, experimental/processing parameters, evidence needs, relevant governance constraints and return/delivery requirements. StegVerse must report which installed capabilities can satisfy each request; which are source-validated only, unsupported or not authentically observed; and the exact first failed transition with correction path. Adaptation occurs in generic schema extensions, adapters and declared processor capabilities, **not** by retroactively changing an evaluator's original evidence, silently substituting a route, adjusting governance constraints for a preferred outcome, or manufacturing missing primary observations. Existing SDK, Manifest Builder, Publisher and Interlock/InTr owners retain their distinct authority boundaries.

**Version independence:** Manifest Builder is a versioned contract inside the SDK, not a separately verified released product. Publisher owns its own package profiles and release identity; synchronization with an SDK target is a compatibility plan, never automatic joint versioning. Interlock/InTr, Master Records and adapters retain independently verified component/version and authority boundaries.

## General capability qualification for all evaluators

Every request has a per-capability qualification record: requirement identifier, requested processing/evidence, installed capability ID and route, exact tested package/build identity, source/provenance evidence, processor-specific result, observed runtime disposition or missing step, permitted next correction, return projection and required Publisher/egress status. No overall PASS may conceal a missing requested capability. Running the capability diagnostic does not admit consequential execution.

A new requirement discovered in an active evaluator experiment that fits an existing general abstraction is eligible for the current development line after native-owner and canonical Registry admission. A broadly useful but noncritical feature enters the next proposed version; a genuinely new processor, route or authority claim needs explicit ownership, compatibility and exact evidence. Neither an individual evaluator nor any single experiment becomes the release authority or changes all other experiments' timing.

## Separation from experiment delivery

Individual experimental protocols, deadlines, participant correspondence and target publication venues reside **only in their own task handoffs**. The generic roadmap may cite a completed cross-framework case as evidence, but its version goals, acceptance gates and adaptive capacity must remain true if that case is cancelled, replaced or postponed. Existing experiment task: `docs/ELAN_HOLD_CHRONOLOGICAL_EVALUATOR_PACKET.md` and the separate time-critical handoff; the experiment is one consumer and proving ground, **not the roadmap's owner**.
